# 第 1 章 AI Agent 基础知识：面试备战手册

基于 [第 1 章原文](chapter1.md) 整理。

---

# 一、开篇概括：核心主张 + 价值锚点

> **核心主张**：Agent 不只是“能聊天的 LLM”，而是由 **LLM（大脑）+ 上下文（眼睛）+ 工具（手脚）** 构成，并通过 ReAct 循环持续“思考—行动—观察”；真正上线后，还必须用 Harness 工程补齐约束、验证和纠正，才能从 Demo 变成可靠产品。
>
> **价值锚点**：这套框架解决了普通 LLM 只能一次性生成文本、不能稳定完成多步骤真实任务的问题。对算法工程师，它提供了 Agent 能力与评估的系统视角；对后端开发，它明确了工具接口、状态、重试、权限和可观测性的工程边界；对 AI 产品经理，它帮助判断何时该用工作流、何时值得引入自主 Agent，以及如何平衡效果、成本、时延与风险。

# 二、知识骨架：关键术语 + 面试话术

- **AI Agent**

  面试时这样说：“我理解 Agent 不是某个单一模型，而是能基于环境信息自主决策、调用工具、接收反馈并推进任务的系统。它的核心价值不在于多说几句话，而在于把多步骤任务真正闭环。”

- **Agent = LLM + 上下文 + 工具**

  面试时这样说：“我通常用‘大脑、眼睛、手脚’解释 Agent：LLM 负责理解和决策，上下文决定它看得到什么，工具决定它做得到什么。三者缺任何一个，Agent 都会明显退化。”

- **LLM / Model（大脑）**

  面试时这样说：“LLM 在 Agent 中的职责不是单纯生成文本，而是理解意图、拆解任务、决定是否调用工具、选择工具和参数，并根据执行结果调整下一步策略。”

- **上下文（Context，眼睛）**

  面试时这样说：“上下文本质上是 Agent 在当前决策点能看到的全部信息。模型能力再强，如果看不到用户状态、工具说明、历史执行结果或领域知识，也会做出错误决策。”

- **静态前缀（Static Prefix）**

  面试时这样说：“静态前缀通常由系统提示词和工具定义构成，负责稳定地告诉模型‘你是谁、有什么权限、能用哪些工具’。它是每轮推理的固定工作环境。”

- **轨迹（Trajectory）**

  面试时这样说：“轨迹是 Agent 的动态执行历史，包括用户消息、模型回复、工具调用和工具结果。它既是 Agent 保持任务连续性的记忆，也是排障、评估和优化的重要数据资产。”

- **系统提示词（System Prompt）**

  面试时这样说：“系统提示词更像 Agent 的岗位说明书，不只是角色设定，还应该承载边界、业务规则、交互原则和升级策略。不过我不会把所有规则都堆进提示词，确定性高的约束应该代码化。”

- **工具定义（Tool Definition）**

  面试时这样说：“工具定义决定模型是否知道自己有什么能力。工具名、用途、参数、示例和边界必须清晰，否则模型会把模糊接口放大成系统性误调用。”

- **工具调用 / Function Calling**

  面试时这样说：“工具调用的关键不只是模型输出一个 JSON，而是完整闭环：声明工具、模型选择工具与参数、框架执行、结果写回上下文、模型据此继续决策。缺少结果回传，Agent 很容易重复调用甚至死循环。”

- **工具分类**

  面试时这样说：“我会从交互方向划分工具：感知工具获取信息，执行工具改变外部状态，协作工具调用子 Agent 或请求人工，事件触发工具启动任务，用户沟通工具负责主动通知和确认。”

- **MCP（Model Context Protocol）**

  面试时这样说：“MCP 可以理解为 Agent 接入外部能力的一种标准化方式，价值在于降低工具生态的接入成本；但协议统一不等于安全，权限、输入校验和审计仍然要在业务侧落实。”

- **ReAct（Reasoning + Acting）**

  面试时这样说：“ReAct 的实际闭环是‘想—做—看—再想’。模型先基于上下文判断下一步，调用工具获取反馈，再更新策略，直到完成或触发停止条件。它适合步骤无法事先完全确定的任务。”

- **观察（Observation）/ 工具结果反馈**

  面试时这样说：“观察不是可有可无的日志，而是闭环控制的反馈信号。没有工具结果，Agent 不知道动作是否成功，也无法纠错、避免重复或调整计划。”

- **内部思考 / Reasoning**

  面试时这样说：“多步任务需要一定的推理连续性，但生产中我更关注可审计的计划、决策摘要和工具轨迹，而不是依赖暴露原始思维文本来做安全或验证。”

- **零样本泛化（Zero-shot Generalization）**

  面试时这样说：“零样本泛化指模型没有示例也能组合已有知识完成新任务。它降低了规则配置成本，但不意味着可以跳过业务验证和工具边界设计。”

- **少样本适应（Few-shot Adaptation）**

  面试时这样说：“少样本就是在提示中给几个高质量范例，让模型快速模仿任务格式或决策模式。它适合快速适配，但不是持久学习，换会话或换上下文后效果可能消失。”

- **后训练（Post-training）**

  面试时这样说：“后训练是把经验固化到模型参数中，通用性强但成本高、迭代慢。我会把它用于高频、稳定、跨任务复用的能力，而不是把变化很快的业务规则都训练进模型。”

- **上下文学习（In-Context Learning）**

  面试时这样说：“上下文学习让模型根据当前提示中的示例快速套用模式，适合短期适配；本质更接近模式匹配，而不是让模型永久学到新规律。”

- **外部化学习（Externalized Learning）**

  面试时这样说：“外部化学习是把知识沉淀为知识库、规则、工具代码和流程。它的优势是可更新、可解释、可审计，特别适合频繁变化的业务知识和合规规则。”

- **模型即 Agent（Model as Agent）**

  面试时这样说：“模型即 Agent 指模型通过后训练把‘何时调用工具、调用哪个、参数怎么传、是否继续’这些决策策略内化了。但工具执行、权限控制和异常恢复仍然在模型外，因此 Harness 不会消失，反而更关键。”

- **Harness 工程**

  面试时这样说：“Harness 是围绕模型的全部工程外壳。最小 Agent 是 LLM、上下文和工具；生产 Agent 还要补上约束、验证、纠正。我的理解是，模型让系统有能力，Harness 让系统有可靠性。”

- **Constrain / Verify / Correct（约束、验证、纠正）**

  面试时这样说：“约束负责事前防越界，例如权限与金额上限；验证负责事后判断动作是否真的成功，例如查数据库状态；纠正负责失败后的重试、回滚、降级或转人工。这三层必须闭环设计。”

- **ACI（Agent-Computer Interface）**

  面试时这样说：“ACI 是从 Agent 的理解方式来设计工具接口。相比传统 API，我会更强调名称语义、参数约束、可逆性提示、返回结构和防呆设计，因为模型只能通过接口理解外部世界。”

- **Poka-yoke（防呆）**

  面试时这样说：“防呆的思路是让错误从设计上难以发生。例如把 `delete_file` 拆成受限目录与高危目录两个工具，或者用枚举替代自由文本参数，而不是期待模型每次都做对。”

- **工作流（Workflow）**

  面试时这样说：“工作流的路径由代码预定义，适合身份核验、支付、审批、订票等强流程和强合规任务。LLM 可以在节点内做理解，但关键节点顺序不应该由模型自由决定。”

- **自主 Agent（Autonomous Agent）**

  面试时这样说：“自主 Agent 的路径由环境反馈动态决定，本质是带工具循环的 LLM。它适合代码修复、深度研究、计算机操作等开放问题，但需要更严格的预算、停止条件、沙盒和人工检查点。”

- **混合编排**

  面试时这样说：“生产上我倾向于混合编排：不可逆、合规性强的路径用工作流锁死；信息搜集、方案生成、异常探索等开放环节交给自主 Agent。这样兼顾灵活性和确定性。”

- **护栏（Guardrails）**

  面试时这样说：“护栏是约束、验证、纠正的分层落地。它不是一个单点分类器，而是输入侧、执行侧、输出侧共同组成的纵深防御体系。”

- **提示注入与越狱**

  面试时这样说：“越狱通常是用户直接诱导模型绕过限制；提示注入则可能藏在网页、文档、邮件等外部内容里，间接操纵 Agent。因此从不可信数据读到的指令不能直接变成高权限动作。”

- **工具风险评级**

  面试时这样说：“工具风险不能只按工具名静态分类，还应结合参数、目标资源、金额、可逆性和用户身份做动态评估。高风险动作需要二次确认、最小权限和完整审计。”

- **人工在回路（Human in the Loop）**

  面试时这样说：“人工介入不是 Agent 失败的遮羞布，而是风险控制和持续学习机制。超过失败阈值、遇到不可逆动作、信心不足或用户意图不清时，都应优雅交接给人。”

- **熔断器（Circuit Breaker）**

  面试时这样说：“当连续失败、重复调用、异常成本持续上升时，熔断器应该停止自动重试，保留上下文和诊断信息，进入降级或人工处理，避免局部错误扩大成系统损失。”

- **可观测性**

  面试时这样说：“Agent 的可观测性至少要覆盖任务轨迹、工具调用、参数摘要、延迟、成本、失败类型、重试次数和最终结果；没有这些数据，就无法判断问题出在模型、上下文、工具还是业务流程。”

# 三、逻辑脉络：问题 → 方案 → 价值

## 问题：普通 LLM 为什么不够

- 普通对话模型通常是“问一句、答一句”，缺乏对真实环境的持续感知与行动能力。
- 面对订票、退款、代码修复、调研等任务，路径往往是多步且动态的，无法靠一次生成完成。
- 仅让模型调用工具也不够：
  - 它可能编造工具、选错工具或填错参数；
  - 看不到工具执行结果时会重复操作，甚至无限循环；
  - 上下文不足会忘记进度、重复工作或做出前后矛盾的决策；
  - 高风险操作可能带来资金、权限、数据泄露或合规问题。
- 因此，真正的问题不是“如何让模型更会说”，而是“如何让模型在不确定环境中安全、可控、可验证地完成任务”。

## 方案：Agent + ReAct + Harness

```text
用户目标 / 事件触发
        ↓
上下文：规则、用户状态、知识、工具定义、历史轨迹
        ↓
LLM：理解意图、规划、选择下一步
        ↓
工具调用：查询 / 执行 / 协作 / 通知
        ↓
观察：工具结果、环境变化、错误信号
        ↓
验证与纠正：校验、重试、回滚、熔断、转人工
        └──────── 回到下一轮决策，直到完成或安全停止
```

核心设计点：

1. **三要素能力层**：LLM 负责决策，上下文负责感知，工具负责行动。
2. **ReAct 执行层**：通过“思考—行动—观察”循环，将一次性回答升级为动态任务推进。
3. **轨迹与状态层**：保存历史消息、工具调用和执行结果，防止失忆、重复和矛盾。
4. **Harness 可靠性层**：补齐上下文、工具、约束、验证、纠正五种能力。
5. **编排层按需选型**：
   - 能一次调用完成：不需要 Agent；
   - 路径固定：工作流；
   - 路径开放、必须动态决策：自主 Agent；
   - 高风险生产场景：工作流与自主 Agent 混合。
6. **安全层**：输入侧防注入与越狱，执行侧做权限与风险分级，输出侧做隐私和内容检查；高风险或反复失败时转人工。

## 价值：落地后能带来什么

- **多步骤自动化**：将“查资料—计算—执行—核验—通知”串成闭环，减少人工在系统间反复切换。
- **更高的任务成功率**：工具结果回写与验证机制让 Agent 能根据事实调整，而非靠猜测继续输出。
- **更好的可靠性**：约束、验证、纠正将“模型偶发错误”限制在可控范围内。
- **更强的可解释与可调试性**：轨迹能回答“它为什么做这一步、工具是否真的成功、在哪里失败”。
- **更适合业务规模化**：将高频经验沉淀为知识库、规则和工具，形成外部化、可迭代的系统能力。
- **更合理的成本控制**：并非所有任务都需要自主循环；用单轮调用、工作流、自主 Agent 分级处理，避免为简单问题付出多轮推理成本。
- **核心竞争力从模型转向工程**：当模型能力逐渐接近时，真正拉开差距的是上下文管理、工具设计、评估、权限、验证和恢复机制。

# 四、面试题预测

## 1. 请简述 Agent 与普通 LLM 的区别。

- **初级回答**

  普通 LLM 主要根据输入生成文本；Agent 则在 LLM 基础上接入上下文和工具，能够规划、调用外部系统、根据结果继续行动，完成多步骤任务。

- **中级回答**

  我会用“LLM 是大脑，Agent 是完整执行系统”来解释。比如普通 LLM 可以告诉用户如何退款，但退款 Agent 能查询订单、校验退款规则、调用退款 API、确认数据库状态并通知用户。

- **高级回答**

  关键区别不只是“有没有工具”，而是是否存在可靠闭环：上下文是否完整、工具结果是否反馈、是否有状态管理、验证、纠正和停止条件。生产级 Agent 应理解为 `Model + Harness`，而不是“模型加几个插件”。

## 2. 为什么说上下文是 Agent 的眼睛？

- **初级回答**

  上下文是模型当前能看到的信息，包括系统提示词、用户请求、历史对话、工具定义和工具结果。

- **中级回答**

  Agent 只能基于看得到的信息做决策。没有工具定义，它不知道能调用什么；没有工具结果，它不知道操作是否成功；没有历史消息，它会忘记已经完成的步骤。

- **高级回答**

  上下文设计是受限资源优化问题：信息不足导致盲目决策，信息过多又会增加成本、干扰注意力并造成上下文膨胀。因此要通过状态摘要、检索、压缩和按需加载，让关键决策信息在正确时机进入上下文。

## 3. ReAct 是什么？完整执行过程是什么？

- **初级回答**

  ReAct 是 Reasoning 和 Acting 的结合：模型先思考，再调用工具行动，再根据结果继续下一步。

- **中级回答**

  更完整地说是“想—做—看—再想”。例如研究 Agent 先搜索资料，再阅读网页，然后用代码分析数据，发现信息不足后继续搜索，最后生成报告。

- **高级回答**

  ReAct 的工程关键不在提示词里写“请一步步思考”，而在于框架是否正确维护轨迹：模型调用、工具执行、结构化结果、状态更新、失败处理都要可追踪。还要有停止条件、最大迭代次数、预算上限和重复检测，避免循环失控。

## 4. 工具结果为什么必须写回上下文？

- **初级回答**

  因为 Agent 要通过工具结果知道操作成功还是失败，并决定下一步。

- **中级回答**

  例如 Agent 调用库存查询接口后，只有看到“缺货”结果，才能推荐替代商品；如果看不到结果，就可能重复查询或直接编造“已经下单成功”。

- **高级回答**

  工具结果是控制系统的反馈信号。生产中应结构化返回状态码、错误类型、可重试标记、资源版本和关键字段，避免模型仅从自然语言描述中猜测结果；关键动作还要由服务端验证最终状态，而不是相信模型的文本结论。

## 5. 如何设计一个好的 Agent 工具接口？

- **初级回答**

  工具名称清晰、参数明确、返回结果规范，并说明使用场景。

- **中级回答**

  我会从 Agent 视角做 ACI 设计：用语义明确的名称，参数尽量使用枚举和结构化字段，提供示例，明确前置条件、权限要求、失败原因和可逆性。

- **高级回答**

  好接口应该防呆。例如不直接暴露万能 `execute_sql`，而是按读写权限拆分；不让模型自由传路径，而是限制工作目录；对删除、付款、退款等操作采用预览—确认—执行的两阶段设计。接口设计本身就是安全控制面。

## 6. “模型即 Agent”是否意味着框架不重要了？

- **初级回答**

  不意味着。模型可以更自主地决定何时调用工具，但工具、权限、安全、状态和错误恢复仍然需要系统实现。

- **中级回答**

  强化学习内化的是工具调用决策策略，不是把搜索引擎、数据库或代码沙盒装进模型参数。模型负责“用不用、怎么用”，外部框架负责“能不能用、安全地怎么执行”。

- **高级回答**

  模型越强，自主动作空间越大，单次错误的影响范围也越大，因此 Harness 的价值会从简单编排转向上下文治理、能力授权、验证、审计、恢复、成本控制和评估。未来框架的竞争点不是堆抽象，而是用最小复杂度提供生产保障。

## 7. 后训练、上下文学习和外部化学习如何选择？

- **初级回答**

  后训练把能力写进模型；上下文学习靠当前提示中的示例快速适配；外部化学习把知识和流程放在知识库、规则或工具里。

- **中级回答**

  高频、稳定、跨场景复用的能力更适合后训练；临时任务格式或风格适配可以用 few-shot；经常变化、需审计、涉及私有知识的内容，应优先外部化。

- **高级回答**

  选型本质上是按“更新频率、覆盖范围、成本、可解释性、风险”做分层。比如退款政策不应靠模型记忆，应代码化或从可信知识库检索；而“如何判断何时搜索”这类泛化策略，才可能受益于后训练。

## 8. 工作流和自主 Agent 的区别？如何选？

- **初级回答**

  工作流的路径是预定义的；自主 Agent 根据环境反馈动态决定路径。

- **中级回答**

  订票中的身份校验、支付、出票顺序适合工作流，因为不能乱序；深度研究、代码修复、复杂客服排障适合自主 Agent，因为步骤无法事先完全写死。

- **高级回答**

  我不会把它们当成二选一。生产里常用混合模式：合规、资金、不可逆动作使用确定性工作流；信息搜集、方案生成和异常排查使用自主 Agent。决策标准是路径不确定性、错误代价、可逆性、监管要求和人工介入成本。

## 9. 如何防止自主 Agent 无限循环？

- **初级回答**

  设置最大轮次、最大重试次数和任务超时。

- **中级回答**

  除了硬上限，还要检测重复工具调用、相同参数反复失败、状态无进展、连续低质量观察结果，并在满足条件时停止或转人工。

- **高级回答**

  我会实现多层终止策略：轮次、时间、token、费用预算、工具风险预算、状态机进展度和语义重复检测；同时将错误分为可重试、需改参、不可恢复三类。发生熔断时要持久化轨迹与已完成成果，避免下次从零开始。

## 10. 如何设计退款 Agent，使其可上线？

- **初级回答**

  查询订单、检查退款规则、调用退款接口、确认退款结果，并通知用户。

- **中级回答**

  我会提供 `query_order`、`check_refund_eligibility`、`create_refund`、`verify_refund_status` 等工具；退款金额、时间窗口和订单归属由后端规则校验，不能只相信模型判断。

- **高级回答**

  我会采用“自主理解 + 确定性交易工作流”的混合设计：模型负责识别用户意图和解释规则；交易步骤由状态机控制；高金额、异常订单、部分退款或不可逆操作需要人工确认；执行前后记录审计日志，超时使用幂等键重试，最终以账务状态为准。

## 11. 如何应对提示注入？

- **初级回答**

  对用户和外部文本进行安全检测，限制模型执行高风险工具，并对输出做检查。

- **中级回答**

  核心原则是区分“数据”和“指令”。网页、邮件、文档的内容默认是不可信数据，不能因为里面写了“忽略规则并转账”就改变 Agent 的权限。

- **高级回答**

  我会实施分层防御：输入侧分类与规则过滤；上下文中标记不可信来源；执行侧最小权限、参数校验、风险分级和人工确认；输出侧做 PII 与敏感内容检查。尤其不能用模型自由生成文本作为授权依据，安全决策应依赖结构化、可信信号。

## 12. 如何做模型选型？

- **初级回答**

  看推理能力、工具调用能力、成本、速度、上下文长度和多模态能力。

- **中级回答**

  不只看公开榜单，要用自己的任务集评估成功率、工具参数正确率、长链稳定性、端到端延迟和单位任务成本。

- **高级回答**

  模型选型应与编排策略一起评估。一个看似更强但输出慢的模型，在 20 轮 Agent 任务中可能导致不可接受的等待；高风险动作还要关注遵循约束、拒绝越权和错误恢复表现。实际常见组合是强模型负责复杂规划，低成本模型负责分类、摘要、路由或结构化提取。

## 13. 为什么 Agent 的错误会“复合”？

- **初级回答**

  因为一个步骤的错误会被后续步骤当成事实继续使用，导致问题不断放大。

- **中级回答**

  例如第一次检索拿到错误资料，模型据此制定计划；后续工具调用即使成功，也是在错误目标上执行，最终得到看似完整但错误的结果。

- **高级回答**

  处理复合错误不能只提升单次模型准确率，还要在关键节点引入独立验证、事实来源追踪、状态不变量、回滚点和人工检查。对高影响动作，应把“模型决定”改为“模型提议 + 系统验证 + 授权执行”。

## 14. Agent 可观测性应该看哪些指标？

- **初级回答**

  看成功率、失败率、延迟、成本和工具调用次数。

- **中级回答**

  还应记录任务轨迹、工具调用参数摘要、错误类型、重试次数、模型轮次、人工接管率和用户最终满意度。

- **高级回答**

  我会建立从业务目标到技术指标的链路：例如退款 Agent 不仅看回答正确率，还看真实退款成功率、错误退款率、平均处理时长、人工升级率、重复调用率和风险拦截率。通过轨迹聚类定位失败模式，再反向优化工具、上下文或流程。

## 15. 如果只能增强模型、上下文、工具三者之一，你选哪个？

- **初级回答**

  一般我会优先增强上下文，因为模型必须先看见正确的信息才能做出正确判断。

- **中级回答**

  但要看瓶颈：模型推理不够时换强模型；没有实时数据或执行能力时补工具；已有能力但经常误判、遗忘和重复时优先优化上下文。

- **高级回答**

  我会先做消融和错误归因，而不是凭直觉选。把失败分成知识缺失、感知缺失、规划缺失、工具不可用、接口误用、执行失败和验证缺失，再决定投资方向。生产场景里，通常先修 Harness 的信息和反馈闭环，收益比盲目换更大模型更稳定。

# 六、追问防御：高压追问与应对话术

## 追问 1：如果 Agent 的规划失败或工具超时，怎么容错？

“我不会让模型自己无限重试。工具返回需要结构化区分：可重试、需要改参数、权限不足、业务不可恢复。可重试错误采用带退避和幂等键的有限重试；需要改参时把错误原因写回上下文；不可恢复时回滚到稳定状态或转人工。同时设置轮次、时间和成本预算，由熔断器防止错误扩散。”

## 追问 2：如果工具成功返回，但返回的是错误数据怎么办？

“工具调用成功不等于业务成功，所以我会把验证拆开。第一层校验响应 schema 和状态码；第二层校验业务不变量，例如退款金额不能超过已支付金额；第三层对高风险动作查询权威数据源确认最终状态。模型文本不能作为成功依据，数据库或交易系统的状态才是事实来源。”

## 追问 3：为什么不把所有业务规则都写进 System Prompt？

“提示词适合表达原则、角色和柔性策略，但不适合承担确定性约束。金额上限、权限、审批顺序、数据访问范围等规则应该在后端或工具层强制校验，因为提示词可被误解、遗漏，也可能受上下文干扰。我的原则是：模型负责判断和提议，代码负责授权和执行边界。”

## 追问 4：Agent 长上下文导致成本和延迟过高，怎么处理？

“先保留任务状态、已验证结论、未完成事项、失败原因和关键证据，而不是原样保留全部对话。具体可以做滚动摘要、分层记忆、检索式回填、工具结果结构化压缩和按需加载工具 schema。目标不是上下文越长越好，而是每个决策点信息刚好够用。”

## 追问 5：怎样判断 Agent 是否真的完成任务，而不是过早宣布完成？

“必须定义机器可验证的完成条件。比如代码 Agent 需要测试通过、静态检查通过并满足验收断言；退款 Agent 需要账务状态确认；研究 Agent 需要覆盖指定问题、给出来源和结论。模型说‘完成了’只是一个信号，不能替代系统验证。”

## 追问 6：工具风险是动态的，如何设计风险控制？

“风险评分至少考虑动作类型、目标资源、参数、影响范围、金额、是否可逆、用户身份和当前环境。比如删除临时文件可以低风险，删除生产配置或系统目录则是高风险。高风险路径进入预览、二次确认、双人审批或人工接管，并保留审计记录。”

## 追问 7：工作流既安全又稳定，为什么还要自主 Agent？

“工作流解决的是可预见流程；自主 Agent 解决的是步骤无法预先枚举的开放问题。比如代码修复、调研和复杂排障，固定路径往往覆盖不了真实环境变化。我的取舍是：能确定就确定，只有不确定性确实带来业务价值时，才引入自主性。”

## 追问 8：多 Agent 协作如何避免重复、冲突和甩锅？

“先明确角色边界、输入输出契约和共享状态所有权，避免多个 Agent 同时修改同一资源。关键资源用锁、版本号、幂等操作和审批机制；协调 Agent 负责分配与汇总；所有 Agent 输出都要可追踪、可验证。多 Agent 不应只是把一个任务拆成更多聊天窗口。”

## 追问 9：人工不在线或回复很慢，Agent 怎么办？

“要按风险分级设计默认策略。低风险任务可以保存草稿、延迟执行或在权限范围内继续；高风险和不可逆操作必须停在安全状态，明确通知用户并保留恢复入口。不能为了‘自主’而替用户做资金、隐私或删除类决策。”

## 追问 10：如何避免过度设计 Harness？

“遵循从简单到复杂的原则：先用单次调用解决，必要时引入工作流，确实需要动态路径才上自主 Agent。Harness 的每个模块都要能对应一个真实失败模式、风险点或评估指标；没有证据支撑的复杂抽象，只会增加调试成本。”

# 八、Agent 经理实战视角（虚构角色）

假设面试官是一位做过客服、研发效能和交易自动化的 Agent 技术主管，叫“周远”。

> **周远的犀利点评**：
> “POC 阶段，大家都在比模型会不会调用工具；生产阶段，我只关心三件事：它会不会越权、做错后能不能发现、发现后会不会把损失扩大。”

## 他可能追问的场景题

1. **设计一个客户服务退款 Agent，你如何确保它不会错退、重复退或假装已退款？**

   期待回答：意图识别可以由 LLM 做；退款资格和金额必须由后端规则校验；交易采用幂等键；最终通过账务系统查验；超时不能直接告诉用户成功；高金额、异常订单或部分退款进入人工审批。

2. **你的 Coding Agent 连续修改代码三次仍然测试失败，你让它继续还是停止？**

   期待回答：不是机械按次数决定。先判断是否有状态进展、失败是否相同、是否出现依赖或环境问题；对重复错误触发熔断；保存补丁、日志、测试输出和已尝试方案，然后交给开发者继续处理。

3. **业务方要求 Agent “尽可能自主”，安全团队要求“所有动作都确认”，你怎么协调？**

   期待回答：先按动作风险分层，而不是用一个规则覆盖全部。低风险可自动执行，中风险预览或异步通知，高风险和不可逆动作必须确认；通过数据逐步扩大自动化范围，而不是一开始就全放开或全禁止。

## 常见扣分点提醒

- 只会背“LLM + 工具”，说不清工具结果、历史轨迹和验证为什么必要。
- 把工具调用成功误认为业务成功，忽略权威状态校验。
- 把全部业务规则塞进 Prompt，忽略后端确定性约束。
- 只讲模型选型，不讲时延、成本、工具调用正确率和长链稳定性。
- 为了显得先进，所有场景都上自主 Agent，忽略工作流在合规和确定性流程中的优势。
- 只说“加护栏”，却讲不清护栏放在输入、执行、输出哪个位置。
- 忽略超时、重复调用、幂等、回滚、熔断、人工接管和审计。
- 把“自主性”理解成“无需人类”，而不是在明确边界内自主完成任务。

# 九、思考题参考答案

## 1. 如果只能给一个 Agent 系统增加一项能力——更强的模型、更丰富的上下文、还是更多的工具——你会选哪个？在什么条件下选择会改变？

### 结论

在没有更多上下文的默认前提下，我会优先选择**更丰富、但经过治理的上下文**。原因不是模型或工具不重要，而是 Agent 的每一步决策都只能基于它当前看得见的信息：不知道用户目标、业务规则、任务进度、可用工具或上一步执行结果时，模型再强也会“盲目决策”，工具再多也可能被错误调用。

### 为什么优先上下文

- 本章的消融实验已经说明，工具定义、工具结果、历史消息和推理连续性缺失时，Agent 会失去行动能力、重复操作、前后矛盾或从头执行任务。
- 丰富上下文能同时解决多个问题：补足实时信息、私有知识、用户偏好、任务状态、业务规则和历史执行证据。
- 它也是最快、最容易迭代的能力：相比训练或替换模型，更新系统提示词、知识库、状态摘要和检索策略的成本更低，且更容易审计。

但“更丰富”不等于“把所有内容都塞进窗口”。真正目标是**在每个决策点提供足够、可信、相关、时效正确的信息**。无关内容过多会提高 token 成本、拉长延迟，甚至干扰模型注意力。

### 什么时候会改变选择

| 当前主要瓶颈 | 优先增加的能力 | 判断依据 |
|---|---|---|
| 模型无法完成多步推理、工具选择或长链任务 | 更强的模型 | 给足上下文和工具后，仍持续出现规划错误、参数错误、长链退化 |
| Agent 缺少实时数据、无法查询系统或不能执行关键动作 | 更多或更好的工具 | 决策基本正确，但“看不到”或“做不到”关键步骤 |
| 任务简单、路径固定、主要问题是流程合规 | 都不是，优先工作流与规则 | 应避免用更强模型或更多工具替代确定性状态机 |
| 业务知识频繁变化、用户个性化强、任务状态容易丢失 | 更丰富的上下文 | 知识、状态、历史或规则缺失是错误主要来源 |
| 工具很多但误用频繁 | 不盲目加工具，优先改 ACI 与约束 | 问题是接口不清、授权过宽或结果不可验证 |

### 面试式总结

“我不会把三者当成静态优先级，而是先做错误归因。默认我会补上下文，因为它决定 Agent 能否看见正确事实；若瓶颈是推理与长程决策，就换更强模型；若瓶颈是无法访问或改变外部世界，就补工具。对于强流程场景，最优解甚至不是三选一，而是用工作流和规则把关键路径确定下来。”

## 2. ReAct 的完整轨迹会造成二次方成本；如何在不丢失关键信息的前提下打破它？

### 问题本质

如果第 1 轮带入 1 单位历史、第 2 轮带入 2 单位历史，直到第 *n* 轮带入 *n* 单位历史，那么累计输入量近似为：

```text
1 + 2 + 3 + ... + n = O(n²)
```

完整轨迹的优势是连续性和可解释性；问题在于，绝大多数旧信息不会在每一轮继续影响决策。解决方向不是粗暴“删历史”，而是把轨迹从“全量重放”升级为“**状态化保留 + 按需取回**”。

### 可组合的解决方案

1. **任务状态摘要（rolling summary）**

   每轮或每完成一个子任务，将历史压缩成稳定状态：目标、约束、已完成项、关键事实、未完成项、失败原因、下一步计划。后续不再携带全部自然语言过程，只携带摘要和最近几轮原始消息。

2. **保留最近窗口 + 长期摘要**

   使用“短期工作记忆 + 长期任务记忆”的两层结构。最近几轮保留原始工具参数和结果，防止丢失局部细节；更早的内容变成结构化摘要。这样既保留局部连贯性，也控制总量。

3. **结构化状态机替代文本回忆**

   将订单号、当前节点、审批状态、已执行工具、重试次数、资源版本、预算等写进外部状态存储，而不是每轮让模型从长文本中重新理解。模型只读“当前状态快照”，框架负责状态一致性。

4. **检索式回填（retrieve on demand）**

   将完整轨迹、网页证据、工具结果存到可检索存储中。当前决策只注入与当前子任务相关的证据，例如“上次支付失败原因”或“用户对转机的偏好”，而不是把所有历史无差别重放。

5. **工具结果规范化与去重**

   工具结果应保留关键字段、状态码、来源、时间戳和资源版本，去除大段冗余日志或重复返回。原始结果可归档，需要时再查；进入上下文的是对下一步有决策价值的最小表示。

6. **分层任务与子 Agent 隔离上下文**

   对大型任务，将研究、计算、执行等子任务拆开。子 Agent 携带本地上下文完成任务，只向主 Agent 返回经过验证的结论、证据和产物引用，避免主轨迹无限膨胀。

7. **按需加载工具定义与知识**

   工具 schema、领域知识和文档不必全部常驻。先根据任务路由，再加载当前阶段真正可用的少量工具和知识，减少静态前缀与动态轨迹的总长度。

### 一个推荐的上下文包

```text
每次调用的上下文 =
  固定安全/角色规则
  + 当前任务状态快照
  + 最近 2～5 轮原始交互
  + 当前子任务相关的检索证据
  + 当前阶段可用的工具定义
  + 必要时可访问的完整轨迹索引
```

这让每轮输入接近常量或缓慢增长；只有任务确实需要回溯时，才通过检索读取历史细节。累计成本便可从无控制的 `O(n²)` 降至接近 `O(n)`，或至少显著低于完整重放。

### 不能丢掉的信息

- 用户的硬约束、授权范围和最终验收标准；
- 已确认的事实、数据来源与时间；
- 已执行的高风险动作及其幂等标识；
- 失败记录、重试次数、不可重复执行的原因；
- 当前任务状态、未完成事项和下一步责任主体。

### 风险与防线

压缩会带来信息丢失或摘要失真的风险。因此，摘要应尽可能结构化并带来源引用；高风险操作前应重新从权威系统读取关键状态；原始轨迹必须保留在外部存储中，可供审计、检索和人工排障。换言之，**不把全部历史塞进上下文，不等于删除历史**。

## 3. “模型即 Agent”与 Harness 工程为何能同时成立？未来框架的核心价值是什么？

### 二者分别解决什么

“模型即 Agent”解决的是**决策能力越来越原生**：经过后训练，模型更会判断何时使用工具、选哪个工具、如何组织长链调用、何时继续检索或停止。

Harness 工程解决的是**现实世界中的可靠执行**：模型之外仍然存在权限、数据、工具实现、状态、网络、成本、审计、异常恢复和安全边界。这些不是仅靠模型内化工具调用策略就能消失的问题。

因此，两者不是替代关系，而是能力边界不同：

```text
模型负责：理解、规划、提议、工具选择、策略调整
Harness 负责：提供上下文、执行工具、授权、验证、纠正、审计、恢复
```

### 为什么模型越强，Harness 反而越重要

- 模型自主性提高后，可执行的动作更多、更快，错误影响面也更大。
- 真实业务规则、用户偏好、私有数据和实时状态变化很快，不适合全部训练进模型。
- 工具是真实系统的入口：数据库、支付、文件、浏览器、生产环境都需要最小权限、参数校验和可回滚机制。
- 生产系统不能只问“模型看起来是否合理”，还要问“动作是否被授权、结果是否真实、失败能否恢复、责任能否追溯”。

### 未来 Agent 框架的核心价值

1. **上下文治理**：按阶段组织系统规则、用户记忆、任务状态、外部知识和轨迹，控制成本并保证信息充分性。
2. **工具生态与 ACI**：提供清晰、安全、可组合、可发现的工具接口，降低模型误用概率。
3. **能力授权与安全策略**：最小权限、风险分级、审批、沙盒、数据隔离和防提示注入。
4. **验证与纠正**：状态不变量、测试、结果核验、重试、回滚、熔断、降级与人工接管。
5. **长任务运行时**：状态持久化、上下文压缩、会话交接、断点续跑、任务队列和事件驱动。
6. **可观测性与评估**：记录轨迹、成本、延迟、工具成功率、失败模式和业务结果，支持持续优化。
7. **多 Agent 协作治理**：角色边界、共享资源一致性、委派协议、冲突处理和权限隔离。

### 面试式总结

“模型即 Agent 让客户端少写一些‘何时调用工具’的编排代码，但不会让生产工程消失。模型是越来越强的驾驶员，Harness 是道路、刹车、导航、保险和维修系统。未来框架不应以堆叠抽象为目标，而应以最小代价把模型能力变成可控、可验证、可恢复的业务执行。”

## 4. 除工具结果缺失外，哪些情况会导致无限循环？如何检测与终止？

### 常见根因

1. **工具连续失败但错误没有被正确分类**：例如权限不足、参数非法或资源不存在，模型却用相同参数反复重试。
2. **目标或完成条件模糊**：用户说“优化一下”“确保没问题”，系统没有机器可验证的完成定义，Agent 会不断继续搜索或修改。
3. **工具结果语义模糊或相互矛盾**：工具只返回“失败”，不告诉失败原因；多个数据源给出冲突结论，模型无法判断该信任谁。
4. **状态没有持久化或更新失败**：动作已经完成，但状态仍显示未完成；Agent 重启后丢失进度，再次执行相同动作。
5. **模型策略退化或重复规划**：模型不断生成同一类计划，或在两个工具、两个方案之间来回切换。
6. **外部环境持续变化**：网页内容、库存、价格或接口状态不断变化，导致原目标永远无法满足。
7. **子 Agent 委派循环**：主 Agent 与子 Agent 相互交回任务，或多个 Agent 重复研究同一问题。
8. **错误的成功判定**：验证器总是拒绝结果，或模型无法触发最终输出，导致即使实际完成也继续行动。
9. **提示注入或恶意内容诱导**：不可信网页不断要求 Agent 继续搜索、执行或绕过停止规则。

### 检测机制

| 检测维度 | 具体信号 |
|---|---|
| 硬预算 | 最大轮次、最大工具调用数、最大重试数、超时、token 与费用上限 |
| 完成进展 | 状态机长期不迁移、待办项不减少、关键指标无改善 |
| 重复行为 | 相同工具 + 相同参数重复调用；相近计划或语义相同的动作循环出现 |
| 错误模式 | 同一错误码连续出现；同一资源连续失败；可重试错误超过阈值 |
| 资源风险 | 在高风险工具上反复尝试；风险预算持续升高 |
| 委派关系 | 委派深度超限、主子 Agent 互相转交、任务哈希重复出现 |
| 验证异常 | 长时间无法满足验收条件，或验证器与执行结果持续冲突 |

### 终止与恢复策略

1. **先暂停，而非盲目继续**：达到硬阈值立刻停止新动作，保存轨迹、状态快照、工具结果和失败分类。
2. **按错误类型处理**：
   - 临时网络异常：有限次数、指数退避重试；
   - 参数或权限错误：要求模型改参、申请授权或转人工；
   - 业务不可恢复：结束自动执行，给出明确解释；
   - 重复规划：切换策略、压缩上下文、重新分解任务，仍无进展则停止。
3. **熔断与降级**：连续失败后关闭相关工具或路径，改为只读查询、生成草稿、请求用户补充信息或交接人工。
4. **优雅交接**：向用户或人工提供“已完成什么、卡在哪里、尝试过什么、还需要什么授权或信息”，而不是只说“失败”。
5. **事后学习**：将循环轨迹归类为评估样本，反查是工具设计、上下文、模型策略还是验证器导致，并修复根因。

## 5. 用“感知—行动—策略”分析一个日常 AI 产品，并提出改进

这里选择 **Coding Agent（以 Cursor 一类产品为例）**。它与本章表格中的 Coding Agent 类型一致，也最适合说明 Agent 如何在真实软件工程中闭环。

### 感知

- 用户需求：自然语言描述、Issue、报错信息、验收要求；
- 代码库：目录结构、源码、配置、依赖关系、Git 历史；
- 开发环境：终端输出、编译报错、测试结果、Linter 结果；
- 外部资料：文档、API 定义、可能的知识库。

### 行动

- 搜索代码、读取和编辑文件；
- 执行终端命令、安装依赖、运行测试；
- 生成补丁、创建分支、提交代码；
- 在受控条件下调用浏览器、文档或子 Agent 做专项检索。

### 策略

典型策略是增量式开发：理解需求 → 定位相关代码 → 形成修改计划 → 小步编辑 → 运行测试 → 根据失败信息调试 → 验证后交付。它本质上是 ReAct：代码、测试和终端输出提供观察，模型基于观察决定下一步。

### 架构是否合理

总体合理，因为软件工程天然是开放问题：实现路径、依赖关系、失败原因往往无法预先写成固定工作流。将代码搜索、编辑、测试和终端作为工具，并持续回读执行结果，符合“上下文 + 工具 + ReAct”的架构。

但它的风险也很明显：上下文会快速膨胀；模型可能修改无关文件；测试通过不等于需求满足；运行命令和修改依赖可能产生安全或成本风险。因此，只有工具循环还不足以支撑生产级 Coding Agent。

### 如果由我设计，可做的改进

1. **显式任务状态栏**：展示目标、当前假设、已修改文件、已运行测试、未完成验证，降低用户和 Agent 的认知断层。
2. **分层权限**：读文件、搜代码默认允许；写文件、执行网络命令、修改依赖、提交代码按风险升级确认。
3. **变更范围约束**：根据 Issue 和初始计划生成允许修改的文件范围；超出范围时要求重新解释或用户确认。
4. **多层验证**：除了单元测试，还要求格式化、静态检查、关键验收测试和 diff 审查；对测试覆盖不到的变更提示残余风险。
5. **上下文压缩与检索**：将旧终端日志、无关文件内容归档为摘要；当前只加载相关模块、符号定义和最新失败信息。
6. **失败熔断与交接**：连续失败时停止大范围改动，输出可复现步骤、失败日志、已尝试方案和推荐的人工排查方向。

## 6. 专门处理航班订票的客服系统，应选工作流还是自主 Agent？能否混用？

### 结论

应选择**工作流为主、自主 Agent 为辅的混合架构**。订票涉及身份、支付、库存锁定、出票、改签退票等高价值且有明确顺序的业务动作，不能完全交给开放式自主决策；但用户意图表达、异常咨询和替代方案推荐又具有开放性，适合引入 Agent。

### 用工作流固定的部分

```text
身份核验
  → 查询航班与报价
  → 用户确认价格与规则
  → 锁定库存
  → 支付授权/扣款
  → 出票
  → 查询出票状态并通知
```

这些步骤应由状态机与后端服务强制控制，至少包括：

- 未完成身份或权限校验前不能操作订单；
- 未获得用户确认前不能扣款；
- 未锁定库存前不能承诺出票；
- 订单、支付、出票必须使用幂等标识；
- 最终状态必须由航司、支付和订单系统的权威回调确认。

### 用自主 Agent 处理的部分

- 将自然语言需求转成结构化搜索条件，例如时间、舱位、预算、是否接受转机；
- 补问缺失信息，识别用户真正的优先级；
- 在多个航班之间做解释性比较，提出替代方案；
- 处理航班取消、行李政策、改签规则等长尾咨询；
- 在确定性流程失败时收集上下文、解释原因并建议下一步。

### 混合流程示例

```text
用户自然语言需求
  ↓
自主 Agent：澄清意图、提取约束、推荐航班
  ↓
工作流：身份核验 → 报价确认 → 库存锁定 → 支付 → 出票
  ↓
自主 Agent：解释结果、处理低风险追问、推荐备选方案
  ↓
高风险异常：人工接管
```

### 为什么不全用自主 Agent

全自主模式会让模型在支付、出票、库存锁定等环节拥有过大的决策自由度，增加乱序、重复扣款、越权操作和审计困难的风险。对于“付款前不能出票”这类规则，最可靠的实现方式是工作流和服务端状态机，而不是提示词提醒。

### 为什么不全用工作流

全工作流对用户表达不完整、异常改签、偏好权衡和开放问答的适应性较差，需要维护大量分支。自主 Agent 可以把不确定性收敛成结构化输入，再把高风险交易交回确定性流程。

## 7. 如何设计动态工具风险评估？

### 核心原则

风险不能只绑定在工具名上，而要评估一次**具体调用**的风险。`delete_file` 本身只是动作类别；删除临时缓存、删除用户工作目录文件、删除生产配置或递归删除目录的实际影响完全不同。

可以将风险写成一个策略函数：

```text
调用风险 = f(动作类型、目标资源、参数组合、权限身份、环境、
            影响范围、可逆性、金额/数据敏感度、当前任务状态、历史行为)
```

### 一套分层评估维度

| 维度 | 需要判断的问题 | `delete_file` 示例 |
|---|---|---|
| 动作性质 | 是读、写、删除、支付还是权限变更？ | 删除天然高于读取 |
| 目标资源 | 资源是否位于受保护区域？ | `tmp/` 低于系统目录、生产配置目录 |
| 影响范围 | 单个对象还是批量、递归、跨账户操作？ | 删除一个临时文件低于递归删除整个目录 |
| 可逆性 | 能否回收、撤销、回滚？ | 回收站可恢复低于永久删除 |
| 数据敏感度 | 是否涉及 PII、财务、密钥或核心业务数据？ | 删除公开缓存低于删除客户数据 |
| 调用主体 | 当前用户、Agent、服务账号拥有什么权限？ | 普通用户会话不应删除系统资源 |
| 环境 | 开发、测试、预发布还是生产？ | 生产环境风险显著上调 |
| 任务上下文 | 是否与已确认任务和用户授权一致？ | 用户要求清理构建缓存，不等于授权删除配置 |
| 异常信号 | 是否来自不可信内容、是否频繁失败或重复尝试？ | 网页注入诱导的删除请求应直接阻断 |

### 风险分数与策略矩阵

可以先用确定性规则命中“硬禁止”项，再计算剩余风险分数。输出的不应只是低、中、高标签，还要有对应执行策略：

| 风险等级 | 典型策略 |
|---|---|
| 低 | 自动执行；记录审计日志 |
| 中 | 预执行校验、参数收紧、向用户展示影响摘要后确认 |
| 高 | 强制人工审批或双重确认；限制作用域；要求可回滚方案 |
| 禁止 | 拒绝执行，说明原因；必要时提供安全替代方案 |

### `delete_file` 的动态示例

```text
delete_file(path="workspace/tmp/build.log")
→ 开发环境、单文件、非敏感、可恢复
→ 低风险：自动执行 + 审计

delete_file(path="/etc/service/config.yaml")
→ 受保护路径、生产环境、可能导致服务中断
→ 高风险：禁止 Agent 直接执行；要求人工审批与变更流程

delete_file(path="customer-data/", recursive=true, permanent=true)
→ 批量、永久、敏感数据
→ 禁止：不可由普通 Agent 会话执行
```

### 工程落地要点

1. **策略在工具执行层实现**，不能只靠模型自我判断。
2. **将高风险工具拆分**：用受限目录、限定资源类型的专用接口替代万能工具。
3. **先预览再执行**：高风险调用先返回影响对象数、路径、金额、权限范围，确认后才生成执行令牌。
4. **最小权限与短期凭证**：每次调用只获取完成当前动作所需的临时能力。
5. **幂等、审计、回滚**：记录谁、何时、基于什么授权执行了什么；能够恢复时优先软删除或版本化。
6. **持续调优**：根据真实误用、拦截和人工审批数据调整风险规则，避免把所有动作都推给人工。

## 8. 受限动作空间在什么场景下优于开放动作空间？

### 结论

开放动作空间带来创造性和适应性，但并非总是更好。当任务的正确选项有限、错误代价高、可验证性强或合规要求严格时，受限动作空间往往更可靠、更便宜、更容易审计。

### 适合受限动作空间的场景

1. **资金与交易操作**

   退款、支付、转账、下单等不应让 Agent 自由生成任意动作。应限制为预定义金额区间、订单范围、审批动作和状态转换。

2. **强监管或高合规流程**

   医疗、金融、政务、保险审批、身份认证等场景，流程和责任边界必须清楚。让 Agent 从允许选项中选择，比生成开放式操作更可控。

3. **安全敏感的系统操作**

   生产环境运维、权限变更、数据删除、密钥管理等，应通过白名单命令、参数模板和沙盒约束能力边界。

4. **任务本身是分类、路由或表单填写**

   如客服工单分流、意图分类、内容审核、审批节点选择。输出空间天然有限，使用枚举或结构化 schema 既降低错误率，也便于自动验证。

5. **高频、简单、低价值的操作**

   如果任务可用少量固定按钮完成，开放 Agent 的多轮推理成本和延迟通常不划算。

6. **训练和评估早期**

   当团队还不了解 Agent 的失败模式时，先收紧动作空间能降低攻击面，收集轨迹后再逐步开放能力。

### 受限空间的收益

- 规则更容易代码化，关键步骤不会乱序；
- 更容易做参数校验、权限控制、测试和审计；
- 模型不易幻觉出不存在的工具或危险参数；
- 成本、延迟和失败范围都更容易预测；
- 提示注入即使影响模型，也较难越出允许的操作集合。

### 取舍与实践建议

受限动作空间的代价是遇到未覆盖的异常时不够灵活。因此最合理的方式不是永久封死，而是做分层能力：

```text
默认：受限、可验证、低风险动作
例外：在沙盒、审批或人工确认后开放更强能力
高风险：始终使用确定性工作流或人工处理
```

这与本章“从简单到复杂”“故障安全默认值”的原则一致：能力默认关闭，经过证明和授权后再逐步开放。

## 9. 用户不在线、响应慢或指令模糊时，Agent 如何优雅移交控制？

### 基本原则：进入安全可恢复状态

“优雅移交”不等于简单停止。Agent 应在不扩大风险的前提下，保存状态、解释当前进度、明确下一步所需信息，并让用户或人工可以从断点恢复。

### 按风险分层的默认行为

| 情况 | Agent 应做什么 |
|---|---|
| 低风险且可逆 | 可继续执行已授权动作，保存草稿或候选方案，等待确认后再提交 |
| 需要用户偏好但不紧急 | 提出少量、明确、可选项式的问题；设置合理过期时间 |
| 高风险、不可逆、涉及资金或隐私 | 立即停在预执行状态，不推测用户意图，不替用户授权 |
| 存在时效压力 | 说明截止时间与不操作的后果；只在用户已预先授权的边界内执行 |
| 用户指令模糊 | 先澄清目标、约束和验收标准；无法澄清时提供方案对比而不是擅自选择 |

### 具体机制

1. **持久化任务状态**

   保存任务目标、已完成步骤、待确认动作、工具结果、资源版本、授权信息与超时时间。用户回来后无需让 Agent 从头理解任务。

2. **把问题问得可操作**

   不问“您想怎么办？”，而问“当前有 A（直飞贵 600 元）和 B（转机省 600 元）两种方案，您是否接受转机？请回复 A 或 B。”将开放决策收敛为有限选项。

3. **使用预授权与默认策略，但边界明确**

   用户可提前配置“低于某价格自动预订”“仅限直飞”“不允许超出预算”等规则。没有明确预授权时，不能把沉默解释成同意。

4. **设置等待与过期机制**

   到期后释放临时资源、停止重试、保留可恢复草稿并通知用户。对于库存锁定、报价等时效信息，应注明状态和重新确认要求。

5. **交接给人工时附带交接包**

   包含用户意图、已收集事实、已执行操作、失败原因、待决策项、风险等级和推荐下一步，避免人工或下一个 Agent 重复问同样的问题。

### 一个订票场景示例

Agent 找到一班符合时间但需转机的低价航班，而用户此前只说“尽量便宜”。正确做法是：查询用户是否预设接受转机；若没有，则展示直飞与转机方案、价格差和风险，等待确认。报价或库存即将过期时，可以提醒截止时间；但不能在没有授权的情况下扣款或出票。

## 10. 哪一条当前 Agent 设计原则可能随模型进步而过时？为什么？

### 候选原则：客户端必须手工编排每一步工具调用

当前不少 Agent 实现会在客户端显式编写复杂编排：先搜什么、再读什么、失败后走哪个分支、何时停止。这一做法在模型工具使用能力不足时很必要，因为模型难以稳定做长程规划。

但随着“模型即 Agent”发展，模型通过后训练越来越能原生完成工具选择、长链调用、信息充分性判断和动态策略调整。未来，**“客户端必须为每个任务手工写细粒度调用编排”**很可能逐渐过时，至少不再是默认方案。

### 为什么它可能过时

- 模型已能把“何时调用、调用哪个、参数怎么传、结果后是否继续”内化为决策能力；
- 手工编排容易把开发者对当前任务的有限理解固化成脆弱规则，对开放任务适应性差；
- 复杂编排代码增加维护成本，模型能力变化后常需要重写；
- 服务端内置工具和原生研究能力正在把一部分循环从客户端迁移出去。

### 但不会过时的部分

这里必须区分“**细粒度策略编排**”和“**工程边界控制**”。前者可能越来越多地交给模型；后者不会因为模型更强而消失：

- 权限、审批、最小授权与安全策略；
- 真实工具执行、身份、支付、审计和数据隔离；
- 结果验证、重试、回滚、熔断和人工介入；
- 业务状态机和不可违反的合规规则；
- 上下文治理、长任务持久化、成本预算和可观测性。

### 更准确的未来原则

未来更合理的表述可能是：

> **把开放任务的策略决策尽量交给模型；把安全、权限、业务不变量、验证与恢复牢牢保留在 Harness。**

这也解释了本章的核心判断：某些今天写在客户端的“教模型怎么一步步做”的逻辑会被模型吸收，但 Harness 工程不会被吃掉，而会把重心转向模型短期内无法替代、也不应该替代的现实世界约束。
