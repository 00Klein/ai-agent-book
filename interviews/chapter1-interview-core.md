# 第 1 章｜AI Agent 入门：高频面试追问笔记

> 基于 `chapter1.md` 提炼。使用方法：先说“结论”，再解释“机制/取舍”，最后用“工程措施或业务例子”收束。不要只背定义。

## 一、30 秒总述（开场答案）

现代 Agent 可概括为 **Agent = LLM + 上下文 + 工具**：LLM 决定下一步策略，上下文提供当前可见的信息，工具把决策变成对外部世界的行动。真正能用于生产的 Agent 还需要 Harness——围绕上下文和工具构建的编排、约束、验证、纠错、可观测与人工接管机制。模型能力提升不会消灭 Harness，反而会提高对其安全性与可靠性的要求。

---

## 二、必会核心题（优先级 S）

### 1. 什么是 AI Agent？它与聊天机器人、工作流有什么区别？

**结论**：Agent 不是“回答问题的 LLM”，而是能在环境反馈下自主决定下一步、调用工具并持续推进目标的系统。

- 相比聊天机器人：聊天机器人多为单轮/少轮生成；Agent 有状态、可行动、会根据工具结果迭代。
- 相比工作流：工作流的路径由开发者预定义；Agent 的路径由模型在运行时动态选择。
- 三要素映射到强化学习：LLM 类似策略（policy），上下文对应观察空间（observation space），工具构成动作空间（action space）。这只是有用的抽象，并不代表所有 Agent 都在实时做 RL。

**追问：没有工具还是 Agent 吗？**

可视为弱 Agent 或具备规划能力的助手，但它无法可靠改变或验证外部世界；生产中“能做事”的 Agent 通常必须具备受控工具能力。

### 2. 为什么说上下文是 Agent 的“眼睛”？上下文有哪些组成？

**结论**：LLM 每个决策点只能基于当前输入作决策；上下文决定它“看得到什么”，因此直接限制其判断、记忆和行动质量。

每次 LLM 调用的上下文包括五部分：

1. 系统提示词：身份、目标、权限、规则，也可承载用户记忆和环境状态。
2. 工具定义：工具名称、用途、参数 schema；决定模型知道哪些能力可用。
3. 用户消息：用户意图，以及可通过 RAG 注入的外部/私有知识。
4. 模型历史消息：此前的推理、文本答复、工具调用，维持任务连贯性。
5. 工具执行结果：真实环境反馈，是下一步纠错与决策的依据。

前两类通常形成**静态前缀**，后三类是不断增长的**动态轨迹**。静态前缀稳定有利于复用与缓存；动态轨迹必须被管理，否则会造成成本、延迟和注意力稀释问题。

**追问：消融掉它们会怎样？**

| 缺少组件 | 典型退化 | 工程含义 |
|---|---|---|
| 工具定义 | 不知道可以调用什么，失去行动能力 | schema 要准确、可发现 |
| 工具结果 | 重复调用同一工具，甚至无限循环 | 结果必须结构化回写轨迹 |
| 模型历史/推理 | 前后决策矛盾 | 保留必要决策状态与交接物 |
| 用户历史 | 任务“失忆”、重复已完成步骤 | 做好状态持久化与摘要 |

### 3. 解释 ReAct 循环；它为什么有效、又有什么问题？

**结论**：ReAct 是“推理/决策—行动—观察反馈—再决策”的闭环；它让模型不只凭内部知识猜测，而是用环境反馈持续修正。

```text
读取上下文 → LLM 决定下一步/工具参数 → 执行工具
      ↑                                      ↓
      └──────── 把工具结果追加回上下文 ────────┘
```

- 有效原因：工具结果把外部世界状态带回模型；每轮都可据此验证假设、修正计划。
- 退出条件：最终输出、模型不再请求工具、发生不可恢复错误、达到轮次/预算/时间上限。
- 核心风险：历史轨迹越长，每轮都重传更长上下文，总 token 成本可呈二次增长；还会出现循环、目标漂移与复合错误。

**追问：如何解决长轨迹和无限循环？**

- 将历史压缩为结构化摘要、任务状态、关键证据和未完成清单；原始日志外置、按需检索。
- 给循环配置最大步数、时间/token/费用预算、重复动作检测、无进展检测、错误重试上限和明确终止状态。
- 使用幂等工具、去重键和可验证的中间里程碑；高风险操作转人工确认。

### 4. 什么是 Harness？为什么模型越强，Harness 反而越重要？

**结论**：Harness 是模型外的工程外壳，用来把有能力但非确定性的模型引导为可靠的任务执行系统。它包括上下文管理、工具接口、编排、安全约束、验证纠错、状态与可观测性。

- “模型即 Agent”意味着模型把何时调用何种工具、如何填参等能力更多内化；但它不会自动解决权限边界、数据可信度、不可逆操作、失败恢复、审计与业务验收。
- 模型越强，能调用的工具越多、行动半径越大，错误的影响也越大，因此更需要 Harness 管控。
- 框架的未来价值不只是串 LLM 调用，而是以尽量小的抽象提供上下文、工具生态、安全、状态恢复、评估与观测能力。

**五项功能的答题框架**：

| Harness 功能 | 面试中应落到的实现 |
|---|---|
| 上下文管理 | 状态栏、摘要、RAG、记忆、token 预算 |
| 工具接入 | 清晰 schema、认证授权、幂等性、超时与错误语义 |
| 编排 | 工作流、Agent loop、状态机、子 Agent |
| 约束与验证 | guardrails、参数校验、测试、结果验收、纠错 |
| 可观测与运营 | trace、日志、指标、评估集、告警、人工升级 |

### 5. 工作流与自主 Agent 如何选择？能否混合？

**结论**：不是二选一。优先顺序应是：先优化单次 LLM 调用/提示词；固定多步任务用工作流；路径无法预先定义、需动态探索时才用自主 Agent。

| 维度 | 工作流 | 自主 Agent |
|---|---|---|
| 路径 | 预定义、确定性强 | 运行时动态决策 |
| 优势 | 可预测、易测试、合规与成本可控 | 适应开放问题、可探索 |
| 代价 | 覆盖不到例外路径 | 延迟/成本高、复合错误风险高 |
| 适用 | 审批、固定表单、标准客服流程 | Coding、研究、Computer Use |

**推荐架构**：用工作流固化合规和高风险环节（身份校验、支付、最终提交），在资料搜集、方案生成等不确定子任务中使用 Agent；在边界处传递结构化状态并做验证。

## 三、高频延展题（优先级 A）

### 6. 工具调用的完整流程及工具设计原则？

流程：在上下文中声明工具 → 模型选择是否调用、选择工具并生成参数 → 框架执行 → 将结构化结果写回上下文 → 模型基于结果决定下一步/答复。

工具设计要点：名称与描述清晰；参数 schema 严格且可校验；返回值机器可读且含错误码；明确权限、超时、重试、幂等语义；对副作用做预览/确认。工具宜具备可组合的基础能力，但“更通用”不等于给生产系统无限权限：通用代码执行必须配合沙箱、最小权限和资源限额。

### 7. 如何理解开放式与受限动作空间？

开放式动作空间（如代码、浏览器操作）灵活、能处理长尾问题，但更难预测和审计；受限动作空间（枚举选项/强 schema）牺牲灵活性换取可控性。

在支付、删除数据、医疗、金融、强合规审批等高风险场景，应优先受限动作空间，或将开放式 Agent 限制在“提出建议/生成草案”，最终执行由受限工作流完成。

### 8. 后训练、上下文学习、外部化学习的区别与取舍？

| 范式 | 将能力放在哪里 | 优势 | 局限 | 适用 |
|---|---|---|---|---|
| 后训练 | 模型参数 | 跨任务泛化强、能力持久 | 训练成本高、更新慢 | 稳定且规模化的能力缺口 |
| 上下文学习 | 当前 prompt/示例 | 快速适配、无需训练 | 会话结束即失效，更像模式匹配 | 少量示例可定义的新任务格式 |
| 外部化学习 | 知识库、记忆、工具代码 | 持久、可解释、易更新 | 需要维护检索与执行质量 | 私有知识、频繁变化规则、确定性流程 |

面试表达关键：不要把“给 few-shot 示例”说成模型参数真正更新；它是在推理时利用上下文模式适配。

### 9. 如何选模型？

按任务而非榜单选择：

- 推理/规划和工具使用质量：复杂开放任务优先。
- 成本与延迟：Agent 是多轮系统，单轮差异会被放大；尤其关注输出 token 速度。
- 上下文、多模态与工具调用：必须匹配输入形态和任务。
- 稳定性、安全性和可观测性：生产环境要看一致性、错误率、供应商 SLA 与审计能力。

最可靠的方式是用代表性任务构建评估集，比较端到端成功率、成本、延迟、安全违规率与人工介入率，而非只比较单轮 benchmark。

### 10. Prompt injection 与 jailbreak 有何差别？

- **Jailbreak**：用户直接试图让模型绕过自身安全规则。
- **Prompt injection**：攻击指令藏在 Agent 读取的外部不可信内容中（网页、邮件、文档），间接操纵模型。

后者对会搜索、读邮件、调用工具的 Agent 尤其危险。防护不应只靠提示词：将外部内容标为不可信数据，隔离指令与数据；最小权限；工具参数校验；高风险动作确认；输入、执行、输出三层护栏与审计。

## 四、安全、护栏与人工接管（优先级 S）

### 11. Guardrails 应放在哪里？

**结论**：使用分层防御，覆盖输入、执行、输出，而不是只在模型前加一个分类器。

| 位置 | 目标 | 示例 |
|---|---|---|
| 输入侧 | 拦截无关、违规、注入输入 | 相关性/安全分类、长度限制、规则过滤 |
| 执行侧 | 控制实际副作用 | 动态风险评级、权限检查、参数策略、人审 |
| 输出侧 | 防泄露与不当输出 | PII 过滤、合规/品牌校验、引用核验 |

### 12. 如何做工具的动态风险评级？

不要只按工具名分级，应按**动作 + 参数 + 目标资源 + 调用上下文**计算风险。例如 `delete_file` 删除临时文件与删除系统目录风险不同。

可采用：资源敏感度、可逆性、权限范围、金额/影响面、环境（生产或沙箱）、调用频率、来源可信度等特征；得到风险等级后分别执行允许、二次校验、最小化执行、人工确认或拒绝。全过程记录审计日志，并通过策略版本化支持回溯。

### 13. 何时引入 Human-in-the-loop？如何“优雅移交”？

触发条件至少包括：超过重试/轮次阈值、置信度或验证失败、敏感/不可逆/高金额操作、权限升级、目标存在歧义。

优雅移交不是只说“请人工处理”，而是交付：用户目标、已经做过的动作及结果、当前状态、风险原因、可选下一步和需要确认的最小问题。若用户不在线，则暂停高风险副作用、保存可恢复状态、设置超时及降级策略；低风险任务可继续完成草稿，但不可擅自提交。

## 五、系统设计题：通用答题模板

以“航班订票客服 Agent”为例：

1. 明确目标、成功标准、边界（查询/改签/退票，是否可直接支付）。
2. 定义上下文：用户身份与订单、实时航班与票规、对话状态；把不可信外部文本与系统指令隔离。
3. 设计工具：查订单、查库存、计算规则、生成方案、确认支付/改签；每个工具含 schema、权限、幂等键与错误码。
4. 编排：查询、身份验证、退款/支付等采用确定性工作流；复杂解释和方案比较使用 Agent。
5. 安全：PII 脱敏，支付/退票/不可逆改签强制确认；按金额和订单状态动态评级。
6. 可靠性：工具结果回写；步数、预算、重试上限；状态机、幂等和补偿机制。
7. 验证与运营：对改签结果做二次核验；记录 trace；监控完成率、转人工率、循环率、延迟、单任务成本和安全拦截率。

## 六、面试易错点与纠正

- **错**：“Agent 就是给 LLM 接几个 API。”  **正**：还需要状态/上下文、反馈循环、编排、验证、安全与运营闭环。
- **错**：“更强模型就不需要框架。”  **正**：模型替代部分决策编排，但不会替代权限、审计、纠错和业务验收。
- **错**：“自主 Agent 一定更高级。”  **正**：固定场景中工作流通常更可靠、更便宜；自主性是有代价的能力。
- **错**：“工具越多越好。”  **正**：工具增加动作空间和攻击面，应按需加载、最小权限、清晰定义。
- **错**：“上下文越长越好。”  **正**：过长会增加成本并稀释重点；应压缩、结构化和按需检索。
- **错**：“安全在上线前加一层过滤。”  **正**：安全是架构的横切问题，要覆盖模型、上下文、工具、协作与运营。

## 七、考前速记

**三要素**：LLM 决策；上下文提供视野；工具提供行动。  
**五类上下文**：系统提示、工具定义、用户消息、模型历史、工具结果。  
**ReAct**：决策—行动—观察—迭代；必须管理轨迹、预算和退出。  
**Harness**：把“不确定的模型能力”变成“可靠的生产执行”。  
**选型原则**：提示词 → 工作流 → 自主 Agent，按需递进。  
**安全原则**：最小权限 + 分层护栏 + 动态风险 + 人工接管 + 可观测/可审计。
