# 第 2 章：上下文工程面试备战手册

> 本手册依据《AI Agent Book》第二章“上下文工程”整理。文末附教材原有的思考题与参考答案提纲，方便面试前连贯复习。

---

## 第一步：开篇概括

> **核心主张**：上下文工程不是“把 Prompt 写得更长”，而是围绕 Agent 在每个决策点“看见什么、以什么结构看见、如何持续更新和压缩”做系统设计；上下文质量往往比单纯换更大模型更决定 Agent 的能力上限。<br>
> **价值锚点**：它把通用 LLM 变成理解业务、遵守流程、能调用工具且可长期运行的 Agent。对算法工程师，它关系到推理质量、Token、延迟和缓存命中；对 AI 产品经理，它关系到业务规则能否稳定落地；对后端/平台工程师，它关系到工具协议、状态管理、安全边界和可观测性。生产里真正拉开差距的，常常不是模型参数量，而是是否把代码、流程、环境、状态和知识以高密度、可信、可复用的方式供给模型。

---

## 第二步：知识骨架（关键术语与面试话术）

- **上下文工程（Context Engineering）**：Agent 的信息供给系统设计。
  - 面试时这样说：“上下文工程不只关心 Prompt 文案，还关心系统指令、工具定义、轨迹、外部知识、环境状态如何组织、注入、缓存和压缩。”
- **上下文窗口（Context Window）**：模型单次可见的信息范围。
  - 面试时这样说：“窗口长不等于效果好；实际还受信息密度、位置偏好和任务相关性影响，长上下文也会出现检索退化。”
- **静态前缀 + 动态轨迹**：System Prompt、工具定义等稳定内容在前；用户消息、模型回复、工具结果持续追加在后。
  - 面试时这样说：“这是缓存、状态管理和压缩设计的基本分层。”
- **消息角色（system / user / assistant / tool）**：定义内容来源与语义。
  - 面试时这样说：“角色不是普通字段。工具结果必须以 `tool` 角色、通过 `tool_call_id` 关联回传，不能拼成普通 user 文本。”
- **无状态 API**：模型不会天然记住上一轮。
  - 面试时这样说：“所谓多轮记忆，本质是 Agent 框架每次重组完整 `messages` 历史；框架的核心职责就是正确管理这份轨迹。”
- **工具调用（Tool Calling）**：模型决策，框架执行。
  - 面试时这样说：“模型只决定调用哪个工具、传什么参数；真实 API 调用、权限校验、结果回传和审计应由 Harness 或 Agent 框架负责。”
- **ReAct 循环**：请求模型 → 返回工具调用 → 框架执行 → 回传结果 → 再请求模型。
  - 面试时这样说：“生产上必须补最大迭代次数、超时、去重、重试和降级，否则 Agent 会在同一工具上循环。”
- **并行工具调用**：无依赖调用并行执行。
  - 面试时这样说：“例如查时间和天气可并行；有数据依赖时再串行，减少端到端时延。”
- **Chat Template**：把结构化 API 消息转换为模型实际处理的 Token 序列。
  - 面试时这样说：“它决定角色边界、工具调用格式和部分模型的思维链处理，所以应优先使用标准 API，不手拼 `USER:` / `ASSISTANT:` 字符串。”
- **思维链 / `reasoning_content`**：多轮 Agent 中可能承载计划与已排除路径。
  - 面试时这样说：“历史思考是否回传必须遵循模型协议。对 Agent 任务，思考往往是一种状态，而不只是可删除废料。”
- **注意力机制（Query / Key / Value）**：当前 Token 用 Query 查询历史 Key，并读取对应 Value。
  - 面试时这样说：“KV Cache 缓存历史 Key 和 Value，减少重复 prefill 计算。”
- **KV Cache**：复用已处理 Token 的中间表示。
  - 面试时这样说：“前缀必须稳定；在系统提示词改一个字符，改动点之后的缓存都会失效。”
- **Prompt Cache**：API 服务层跨请求复用相同前缀的计算结果。
  - 面试时这样说：“它和 KV Cache 都依赖稳定前缀，但 Prompt Cache 更直接影响在线 Agent 的账单、首 Token 延迟和架构取舍。”
- **位置偏好 / Lost in the Middle**：开头和结尾往往更容易被模型关注。
  - 面试时这样说：“稳定的关键规则放前缀，动态、影响当前决策的状态放末尾。”
- **缓存友好上下文布局**：静态内容前置、动态内容追加。
  - 面试时这样说：“当前时间、用户余额、动态工具排序都不应写进 System Prompt；它们应通过末尾状态消息或工具查询提供。”
- **系统提示词（System Prompt）**：Agent 的员工手册。
  - 面试时这样说：“我用‘聪明的新员工读完是否知道怎么做’检验它，内容应覆盖身份、流程、约束、业务边界和输出要求。”
- **结构化提示与流程驱动 Prompt**：XML/Markdown 的层次与 SOP。
  - 面试时这样说：“不要堆零散规则；按校验、分类、执行、验证写成流程，模型能知道当前阶段和异常处理路径。”
- **业务规则细化**：把模糊偏好写成可执行的条件、阈值、禁止项与边界案例。
  - 面试时这样说：“模型应在明确框架内推理，不应替产品做商业规则裁决。”
- **Few-shot 示例**：用少量输入输出示例表达难以抽象的风格或格式。
  - 面试时这样说：“两三个覆盖边界的固定示例通常优于大量同质示例；示例集需稳定，避免逐请求动态替换导致缓存失效。”
- **工具定义设计**：描述工具使用边界、参数语义、反例、例子和协作关系。
  - 面试时这样说：“章节消融实验中移除描述文本后，工具调用错误率增加 45%，所以 schema 不是只有函数签名。”
- **工具渐进式披露 / Tool Search**：常驻名称与简述，按需加载完整 schema。
  - 面试时这样说：“它把大工具集从巨型静态前缀中拆出来，降低 Token 占用，又避免频繁重排工具导致缓存失效。”
- **提示注入（Prompt Injection）**：不可信外部内容伪装成指令、劫持 Agent 行为。
  - 面试时这样说：“Agent 有工具权限后，注入风险从不当输出升级为泄露、写文件、发邮件甚至不可逆操作。”
- **来源标记与指令/数据分离**：外部内容需标记来源、保持 role 结构。
  - 面试时这样说：“Prompt 层只是一道防线；还要用最小权限、沙盒、高风险确认和审计实现纵深防御。”
- **Agent Skills**：可版本化、可组合、按需加载的领域能力包。
  - 面试时这样说：“Skill 把巨型 Prompt 拆成知识模块，先给目录，再按任务加载操作手册、细则和脚本。”
- **渐进式披露（Progressive Disclosure）**：元数据 → 核心流程 → 细则/脚本的三层加载。
  - 面试时这样说：“目标是让模型知道它有哪些能力，而不必每轮背下全部手册。”
- **Skill 路由描述**：写作 `Use when` / `Don't use when` 的路由条件。
  - 面试时这样说：“反例很重要；宽泛的‘help with backend’会误触发，真正有效的是明确何时不该用。”
- **Agent 状态栏（Agent Status Bar）**：末尾注入的 TODO、计数、错误、环境、时间和能力清单。
  - 面试时这样说：“它把分散在长轨迹中的隐式状态提炼成模型可直接读取的显式知识。”
- **上下文蒸馏（Context Distillation）**：预先提炼结论供模型检索。
  - 面试时这样说：“不要让模型每轮扫描历史重新数数；程序维护高可靠键值状态，模型直接使用结论。”
- **状态栏可靠性**：状态栏是高信任信息。
  - 面试时这样说：“计数、预算、状态迁移优先由确定性代码维护；新问题维度未覆盖时保留原始证据，不能让不完整摘要成为假权威。”
- **时间感（Time Sense）**：紧迫度、坚持度、警觉度。
  - 面试时这样说：“仅注入 `elapsed_ms` 不够，状态栏还要告诉模型怎么行动，例如慢调用要诊断、重试到上限要切换策略。”
- **上下文腐化（Context Rot）**：装得下但找不到。
  - 面试时这样说：“它不同于窗口溢出，常由无关工具输出、重复信息和过期状态造成。”
- **上下文感知压缩**：结合任务目标和既有事实进行摘要。
  - 面试时这样说：“压缩不仅为省长度，更是把需要重复思考的原始记录转为高密度、任务相关、可检索的知识。”
- **分层压缩**：预算控制、删除噪声、轻量编辑、归档摘要、全量压缩。
  - 面试时这样说：“先做低成本、低扰动处理，LLM 全量压缩作为兜底，并用熔断器防压缩失败循环。”
- **子 Agent 上下文隔离**：探索在子上下文完成，只回传结论。
  - 面试时这样说：“隔离优于事后压缩；主 Agent 不被海量中间过程污染，但委派描述必须自包含、目标明确。”

## 第三步：逻辑脉络（问题 → 方案 → 价值）

### 问题

LLM 不知道企业的代码结构、业务规则、流程规范、环境状态和任务进度。即使窗口很长，也仍有四类典型失效：

1. **信息缺失**：没有业务背景，只能凭通用知识猜测。
2. **结构混乱**：规则、工具结果、外部数据与真实指令混在一起，模型不清楚来源和优先级。
3. **轨迹膨胀**：多轮工具调用导致遗忘、重复、窗口溢出和上下文腐化。
4. **性能与安全失控**：动态修改前缀破坏缓存；网页、邮件、文档和第三方 Skill 都可能成为注入入口。

### 方案

1. 使用标准 API 消息结构：system 定义规则，user 承载需求，assistant 保存决策，tool 回传观察，框架维护完整轨迹。
2. 用缓存友好布局：固定系统规则、工具定义和示例；所有动态信息仅在末尾追加。
3. 用结构化、流程驱动、业务规则细化的 System Prompt 约束行为；用少量高质量 Few-shot 解决难以规则化的表达。
4. 用 Skills 与 Tool Search 按需加载知识和工具，而非一次性塞进前缀。
5. 用状态栏维护 TODO、调用次数、错误、环境与时间，把隐式状态变成显式状态。
6. 用任务感知的分层压缩控制轨迹长度；对高体积探索优先使用子 Agent 隔离。
7. 用来源标记、角色隔离、最小权限、沙盒与人工确认抵御提示注入。

### 价值

- **正确性**：章节实验显示，打乱相同提示词内容会使任务成功率下降超过 30%；去掉工具描述后工具调用错误率增加 45%。
- **效率**：稳定前缀提高缓存复用；上下文感知压缩在本章实验中减少了 75% 以上 Token。
- **可靠性**：状态栏、TODO、错误建议和调用计数减少盲目重试与漏任务。
- **可维护性**：Skill、Prompt 模块和工具描述可独立版本化、测试和复用。
- **安全性**：将不可信外部数据与高权限执行能力隔离，降低注入带来的真实操作风险。

## 第四步：面试题预测

### 1. 什么是上下文工程？和 Prompt Engineering 有什么区别？

- **初级**：Prompt Engineering 关注提示词；上下文工程关注模型每次调用看到的全部信息，包括系统提示词、历史、工具、状态和知识。
- **中级**：它是 Agent 的信息供给系统，还要考虑消息角色、注入位置、缓存、压缩与安全。
- **高级**：它既是技术问题也是组织问题。企业知识不文档化、不结构化，再强模型也无法可靠执行具体业务。

### 2. 为什么上下文质量比模型大小更决定 Agent 能力？

- **初级**：模型不天然知道公司的业务规则和实时环境。
- **中级**：Coding Agent 没有代码结构、测试环境和流程规范时，可能写出可运行但不符合项目要求的改动。
- **高级**：优化应先排查信息缺失、规则冲突、工具描述与状态管理，而不是直接换更大模型。

### 3. Agent 工具调用循环如何工作？

- **初级**：模型决定调用工具，框架执行并回传结果，模型据此继续调用或给最终答案。
- **中级**：工具结果必须用 `tool` 角色和 `tool_call_id` 对应，框架而非模型拥有执行权限。
- **高级**：生产实现需要参数校验、超时、重试、幂等、并行调度、最大迭代数、循环检测和审计。

### 4. 为什么不能把工具结果拼成普通 user 消息？

- **初级**：模型可能误以为这是新的用户请求。
- **中级**：Chat Template 会按角色生成不同 Token；错标工具结果可能破坏多轮思考与工具调用语义。
- **高级**：不同模型的 reasoning 回传规则不同，必须遵循供应商的标准消息与模板协议。

### 5. KV Cache 是什么，为什么会影响 Agent 架构？

- **初级**：它缓存前文 Key、Value，避免重复计算。
- **中级**：系统提示词中的动态时间、动态配置或工具重排会让前缀失效，导致延迟和成本上升。
- **高级**：缓存是架构约束。Prompt 片段应区分静态与动态；子 Agent、会话恢复和工具结果替换也要保持缓存键一致。

### 6. KV Cache 和 Prompt Cache 的区别？

- **初级**：KV Cache 偏模型推理内部；Prompt Cache 偏 API 服务层跨请求的前缀复用。
- **中级**：二者都要求稳定前缀，但 Prompt Cache 更直接影响在线调用的费用和 TTFT。
- **高级**：不同服务商的自动命中、最小长度、TTL 和计费不同，生产方案必须结合目标模型验证。

### 7. 如何设计缓存友好的上下文？

- **初级**：系统提示词和工具定义稳定，动态信息追加在末尾。
- **中级**：固定工具排序和 Few-shot 示例，状态通过末尾状态栏或工具查询提供。
- **高级**：划分全局可缓存层、会话静态层、动态轨迹层，并监控缓存命中、TTFT、Token 和前缀变体数量。

### 8. System Prompt 如何写得可靠？

- **初级**：明确角色、任务、限制和输出格式。
- **中级**：用 XML/Markdown 分层，按 SOP 组织，细化业务规则到阈值、禁止项和边界案例。
- **高级**：Prompt 应版本化、评审、回归测试与消融实验；产品负责业务规则，工程负责结构、协议与可观测性。

### 9. Few-shot 什么时候有用？

- **初级**：难以用规则描述的风格、格式和输出结构适合用示例。
- **中级**：两三个覆盖边界的示例通常足够，大量同质示例只会占用 Token。
- **高级**：动态检索和替换前部示例会破坏缓存，宜按任务类型维护固定示例集，并用评测验证收益。

### 10. 如何防范 Prompt Injection？

- **初级**：把网页、邮件、文档等外部输入视作不可信数据，不执行其隐藏指令。
- **中级**：做来源标记、严格 role 传递、可疑输入清洗和高风险操作确认。
- **高级**：Prompt 防御不够，还要最小权限、读写分离、沙盒、敏感数据隔离、网络出站限制和审计。

### 11. 什么是 Agent Skills，为什么不把知识都写进 System Prompt？

- **初级**：Skill 是按需加载的领域能力包。
- **中级**：全部塞入 System Prompt 会浪费 Token、稀释注意力、难维护，并在更新时破坏缓存。
- **高级**：Skill 三层渐进披露：元数据、核心流程、细则/脚本；它也让能力具备版本管理、测试和生态复用能力。

### 12. Skill 如何避免误触发？

- **初级**：清晰描述 Skill 的用途。
- **中级**：描述应写成 `Use when` / `Don't use when`，尤其要提供反例。
- **高级**：把路由当分类问题评估召回率、误触发率和漏触发率；结合规则、任务分类器或候选 Skill 推荐，弥补模型元认知不足。

### 13. 什么是 Agent 状态栏，它解决什么问题？

- **初级**：状态栏是在上下文末尾注入的 TODO、调用次数、时间、错误和环境摘要。
- **中级**：它把长轨迹中隐式、分散的状态变为可直接检索的键值知识，避免模型重复扫描和统计。
- **高级**：它既是上下文蒸馏，也是注意力引导；最有价值的是模型无法自行推断的真实环境观测，例如测试结果和工具运行状态。

### 14. 状态栏如何更新：替换还是持续追加？

- **初级**：替换能保持状态最新；追加能保存历史。
- **中级**：替换会让替换点之后的缓存失效；追加缓存友好，但会累积过期状态。
- **高级**：长轨迹且高频更新倾向追加并声明“最新为准”；短轨迹或大状态快照可以替换，依据缓存重建成本、状态大小和风险取舍。

### 15. 如何保障状态栏正确？

- **初级**：状态栏错误会误导模型，因此需要校验。
- **中级**：调用计数、预算和状态机由确定性代码维护，不让 LLM 批量总结长历史。
- **高级**：像管理生产数据一样管理状态栏：定义 schema、来源、刷新策略、质量指标、审计和回滚；未覆盖新问题维度时保留原文。

### 16. 什么是 Context Rot，如何治理？

- **初级**：信息太多时，模型找不到关键内容。
- **中级**：它是“装得下但找不到”，不同于窗口溢出；重复工具输出、无关资料、过期状态都会造成它。
- **高级**：重点不是盲目扩窗口，而是按需加载、状态蒸馏、任务感知压缩、保留关键决策、删除噪声和隔离探索任务。

### 17. 如何设计上下文压缩策略？

- **初级**：过长时把旧工具结果和对话压成摘要。
- **中级**：保留时间、主体、约束、验证状态和唯一标识；接近阈值时批量压缩，避免每轮压缩。
- **高级**：采用工具结果预算、噪声删除、API 微压缩、归档摘要、LLM 全量压缩的分层设计；摘要带来源索引，连续失败要熔断。

### 18. 压缩与 KV Cache 是否矛盾？

- **初级**：压缩改历史，可能造成部分缓存失效。
- **中级**：二者可以共存：固定 System Prompt 与工具定义，仅在调用间压缩工具结果，以局部缓存重建换取不超窗。
- **高级**：关键在位置和频率。频繁小压缩会不断重建缓存；阈值触发的批量压缩更合适，高体积探索则优先交给子 Agent。

### 19. 子 Agent 隔离和上下文压缩如何取舍？

- **初级**：压缩是事后减法，隔离是不让中间信息进入主上下文。
- **中级**：大范围搜索、读取大量文件等任务适合子 Agent，只回传结论和证据。
- **高级**：隔离维持主 Agent 的高信息密度和稳定缓存；委派必须包含明确目标、范围、验收标准、必要背景与返回格式。

### 20. 如何定位 Agent 表现差是 Prompt、工具还是模型问题？

- **初级**：先复现并查看日志。
- **中级**：做消融实验，分别移除或替换提示词结构、工具描述、状态栏、Skill、压缩策略，比较指标。
- **高级**：建立离线基准与线上闭环，按任务类型分桶，结合成功率、工具参数错误率、迭代数、Token、缓存命中、安全拦截等指标做归因。

## 第六步：追问防御

- **如果 Agent 规划失败或工具连续超时，怎么容错？**
  - “为每个工具配置超时、重试上限、幂等键和降级路径；状态栏记录累计失败次数与建议动作。达到阈值后切换工具、缩小范围、请求补充信息或安全终止，而非盲重试。”
- **状态栏错了怎么办？**
  - “状态栏有 schema、来源和校验。低风险统计可由确定性代码维护；高风险状态增加交叉校验、时间戳和可追溯日志。状态不确定时保留原始证据并显式标注。”
- **状态栏和原始轨迹冲突时听谁的？**
  - “不能一概默认状态栏。确定性统计可优先用状态栏；高风险或状态栏覆盖不完整时必须回查原始证据，并根据来源、更新时间和置信等级裁决。”
- **如何避免压缩丢重要事实？**
  - “先定义不可压缩字段：架构决策、关键约束、验证结果、未完成 TODO、文件变更、UUID、URL、hash、端口等；摘要保留来源索引，支持回溯。”
- **为什么不每轮都压缩？**
  - “每轮压缩增加 LLM 调用、损失细节且反复破坏缓存。按 Token 预算阈值批量触发，通常能兼顾完整性和成本。”
- **网页指令和用户指令冲突时如何处理？**
  - “网页仅是不可信数据，不能升级为指令。即使模型受诱导，工具权限、沙盒和高风险确认也应阻止越权动作。”
- **第三方 Skill 是否也是 Prompt Injection？**
  - “是，而且风险更高。Skill 应有来源、版本、审查、签名或白名单；捆绑脚本也需要依赖审计与隔离执行。”
- **大量工具如何兼顾可发现性与缓存？**
  - “少量核心工具固定在前缀，长尾能力走 Tool Search / 延迟加载；完整 schema 被加载后保留在原位置，不反复重排或搬到末尾。”
- **子 Agent 回传错误摘要怎么办？**
  - “要求它分开返回结论、证据位置、置信度和未验证项；主 Agent 对关键结论二次验证，高风险决策可以回溯原始工具结果。”
- **如何证明上下文优化有效？**
  - “同时看成功率、参数错误率、迭代次数、输入输出 Token、TTFT、端到端延迟、缓存命中、压缩失败率和安全拦截率，并用消融实验确认因果贡献。”

## 第八步：Agent 经理实战视角

假设这位负责人叫 **周岚**，是一位负责客服、代码助手和知识运营 Agent 的企业平台负责人。

> **一句话犀利点评**：POC 阶段大家都在比模型会不会调用工具；生产阶段真正拉开差距的，是你的 Agent 在第 30 轮还记不记得约束、能不能停下来、错了能不能安全恢复。

### 他可能问的场景题

1. **设计退款客服 Agent：用户可查询订单、提交退款、发送邮件。你如何组织上下文与权限？**
   - 期待点：稳定的退款政策与工具 schema；订单、身份、当前状态动态注入；邮件内容标为不可信；退款和外发邮件需权限校验、幂等和用户确认；状态栏维护退款阶段、调用次数与失败原因。
2. **Coding Agent 读了上百个文件，开始反复搜索同一目录、修改错误文件。如何止血？**
   - 期待点：检查轨迹与工具日志；加入调用计数、工作区状态、TODO 和错误建议；限制重复读取；将大范围检索委派给子 Agent；压缩噪声输出但保留文件修改和测试结果。
3. **System Prompt 被十几位同事陆续修改，线上成功率越来越不稳定。如何治理？**
   - 期待点：Prompt 版本管理、模块化、所有权、评审、黄金测试集、A/B 与消融实验；将业务政策与技术框架分层，禁止临时规则无序堆叠；监控缓存命中与前缀变体。

### 常见扣分点提醒

- 只会说“加 RAG、加长上下文、换大模型”，却不谈信息来源、结构、位置和生命周期。
- 把模型当直接执行者，不谈参数校验、超时、幂等、权限、审计和错误恢复。
- 把动态时间、用户状态塞进 System Prompt，不知道这会破坏缓存。
- 只背“状态栏有效”，却不谈状态可靠性、投毒风险和回查原始证据。
- 只谈 Prompt Injection 的提示词防御，不谈最小权限、沙盒、确认等执行层防线。
- 只谈“压缩省 Token”，却忽略关键决策、验证状态和唯一标识的保留与回溯。

# 附录：第二章思考题与参考答案

> 以下内容整理自 [思考题参考答案](思考题参考答案.md) 的“第二章 上下文工程”部分。题目为开放题，答案是参考提纲，不是唯一标准答案。

## 思考题 1

**实验 2-3 发现，滑动窗口对话历史会导致 Agent 反复执行相同的工具调用。但完整保留历史又会让上下文不断膨胀。设计一种策略，既能避免信息丢失，又能控制上下文长度，且不破坏 KV Cache 前缀。**

**参考答案：**

1. 用压缩代替丢弃：消息只追加、不删改；接近阈值（如窗口 80%）时，批量压缩旧 `tool results`。
2. 使用分层机制：大输出落盘只留摘要，噪声直接删除，归档式摘要保留任务脉络。
3. 对高体积探索使用子 Agent 隔离，让大部分中间状态根本不进入主上下文。

## 思考题 2

**Qwen3 的 Chat Template 思维链保留机制只保留“最后一个真实用户消息之后”的思考。如果一个 ReAct 循环跨越上百轮工具调用，累积思考内容可能消耗大量上下文。你会如何修改该机制？DeepSeek R1 曾要求剥离全部历史思考，而 DeepSeek V4 反转为强制回传全部 `reasoning_content`。两者的利弊是什么，这一反转说明什么？**

**参考答案：**

- 修改方向：完整保留最近若干轮思考；窗口外按 **Token 预算** 而非固定轮数触发滚动压缩，形成结构化状态栏，记录当前目标、已确认事实、已排除路径和待办。压缩只发生一次且位置固定，使缓存重建成为一次性代价，而非每轮付出。
- **R1 剥离历史思考**：节省 Token、前缀稳定且缓存友好，也符合其训练分布；缺点是每轮趋近于从零推理，容易丢失长程计划、重复犯错。
- **V4 强制回传思考**：优点是思路连贯，更适合长程 Agent 任务；缺点是 Token 成本高、前缀持续膨胀，且难从非 thinking 模式无缝切换。
- 这一反转说明：对纯对话，思考可能是废料；对 Agent，思考常常就是状态，行业实践已明显倾向后者。

## 思考题 3

**上下文感知压缩实验中，从约 148K 个字符压缩到约 2,000 个字符，是否有不可逆信息损失风险？如何解决？**

**参考答案：**

有风险。压缩是有损投影，后续问题一旦落在未保留维度上，答案就可能失真。解决方案是：

1. 采用“**有损压缩 + 无损索引**”：每条关键事实附来源 URL，允许回溯。
2. 原始工具输出存磁盘，模型默认看摘要预览。
3. 显式定义保留优先级：架构决策、语义完整性（时间、公司名等）、验证状态、UUID、hash 等标识符必须保留。
4. 使用自适应窗口化，推迟到真正接近预算时才压缩，尽量保留早期原始信息。

## 思考题 4

**Agent 状态栏将隐式状态显式化。但如果状态栏本身有错误，例如工具计数器有 bug，Agent 可能据此做有害决策。如何缓解这种“元信息可靠性”问题？**

**参考答案：**

模型会高度信任状态栏，错误会被原样传导。因此：

1. 用确定性代码维护状态，避免让 LLM 一次性统计长历史；若必须用 LLM，应逐条抽取后由代码汇总。
2. 将状态栏准确率作为一线生产指标监控。
3. 状态只能来自真实世界的可靠观测，并防止将外部不可信数据写入状态栏造成投毒。

## 思考题 5

**提示工程消融实验表明，信息组织混乱会使成功率下降 30% 以上。实际中系统提示词常由多人长期维护，如何防止 Prompt“熵增”？**

**参考答案：**

1. 把 Prompt 当代码管理：版本控制、评审；产品经理负责业务规则，工程师负责准确编码与结构实现。
2. 建立类似 Tau-Bench 的回归基准；每次改动前后运行评测，必要时做消融实验定位影响。
3. 强制结构化：采用 XML/Markdown 分层和 SOP 流程驱动，而不是规则堆砌。
4. 片段按“可缓存 / 破坏缓存”分类命名；动态内容统一放在缓存边界之后。
5. 膨胀的领域内容拆成 Skills 按需加载。

## 思考题 6

**如果“上下文学习本质上是检索而非推理”这一论断成立，应如何突破把更多信息塞进上下文的局限？**

**参考答案：**

给“只有一半的检索引擎”补上提炼层：

1. 使用上下文蒸馏 / 状态栏，由代码提前计算关键结论。
2. 主动压缩，把原始记录转换为高密度结构化知识。
3. 使用子 Agent 隔离，让噪声不进入主上下文。
4. 将交互作为第三轴：让外部工具和验证器把模型自己推不出的真实观测写回上下文。
5. 探索可编辑、可组合的 KV Cache“笔记”和跨会话的持久记忆沉淀。

## 思考题 7

**Skills 的渐进式披露依赖 Agent 判断是否需要加载。如果模型不知道自己不知道什么，如何解决这个元认知问题？**

**参考答案：**

1. 将 Skill 的名称和描述作为轻量元数据常驻上下文，让模型始终知道自己有哪些能力。
2. 将 `description` 写成路由条件，而不是功能宣传：明确 `Use when` 和 `Don't use when`，避免宽泛描述导致误触发。

## 思考题 8

**Agent 从 SKILL 文件动态读取提示词后，能否正确遵循？不同模型对 Skills 模式的支持有何区别？**

**参考答案：**

取决于注入位置与模型训练：

- 注入 `system prompt` 时指令遵循最强，但会在加载新 Skill 时破坏 KV Cache。
- 作为普通文件读到上下文中间时不影响静态前缀，但模型可能将其当普通参考资料，指令遵循较弱。
- 生产常用做法是：元数据放末尾，完整内容由专用 Skill 工具按需加载。模型对自己主动调用工具返回的内容通常有更强执行倾向；不同模型对“中间位置指令”的支持差异显著，应按对应生态的训练约定和文档验证。

## 思考题 9

**动态时间戳和工具列表顺序都会破坏 KV Cache 前缀命中。在工具很多且工具集频繁变动的生产系统中，如何设计上下文布局以最大化缓存命中？**

**参考答案：**

1. 保留少量稳定核心工具与通用执行器；将具体领域能力移到 Skills 或工具渐进式披露中。
2. 静态前缀中的工具定义冻结并保持固定顺序；动态信息只追加到轨迹末尾。
3. 子 Agent 与父 Agent 共享模型配置、系统提示词、工具定义和消息前缀，尽量字节级对齐，以复用缓存。
4. 已加载的工具 schema 保持在轨迹原位置，不频繁修改、删除或重排；同时监控缓存 TTL、命中率和前缀变体。
